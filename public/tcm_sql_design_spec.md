# 中醫處方實驗室 — 資料庫設計文件

**性質：課堂作業正式設計規格（不含程式碼）**  
**目標部署：GitHub Pages；瀏覽器內 SQLite；無伺服器端與登入。**  
**繳交期限：2026-11-19（四）23:59。**

## 一、整體定位與實作決策

**正式名稱**：中醫處方實驗室（TCM SQL Lab）。

**一句話介紹**：使用一組經過教學化整理的中醫病例、證型、症狀、方劑與藥材資料，在瀏覽器裡練習真實 SQL 查詢，觀察條件、資料表連結與聚合方式如何影響結果。

**核心目標**：對齊授課教師四點要求：案例背景、資料庫設計、可修改執行的 SQL 查詢、相同問題下的結果比較。作品兼具醫療場景敘事、資料庫正規化、可重現結果與 SQL 教學。

**範圍**：單頁靜態應用，四章導覽；真正的 SQL 編輯器、結果表格、錯誤回報、基準結果／修改結果差異比較；可讀 ERD、欄位字典、樣本資料。數據資料在前端以固定種子載入 SQLite；每次執行從相同初始資料開始，維持答案可重現。

## 二、作業要求 ① 案例背景（可直接放網站）

### 2.1 需求情境

> 一間中醫教學診所彙整了一批門診紀錄。每份病例包含主訴、望舌、切脈、症狀、證型及使用過的示例方劑；方劑又由不同藥材組成。研究助理經常需要回答「某證型有幾個病例？」「同時出現兩種症狀的病例有哪些？」「哪個方劑的使用紀錄最多？」「某方包含哪些藥材？」等問題。將資料分成彼此關聯的資料表後，就可以用 SQL 重現查詢、統計與交叉分析，降低人工翻查紀錄的成本。

### 2.2 三種使用者與操作任務

| 使用者 | 實際問題 | 需要的資料庫能力 |
|---|---|---|
| 中醫師／診所研究人員 | 檢視相同證型的病例與示例處方 | 病例、證型、方劑多表查詢 |
| 診所研究助理 | 統計常見證型、常見症狀、處方使用次數 | 條件篩選、彙總、分組、排序 |
| 資料庫課程學生 | 修改 SQL、分析執行結果與差異 | SQL 編輯、執行、預期結果、比較、錯誤說明 |

### 2.3 主要操作情境

1. 研究助理先選擇「找出肝鬱脾虛的病例」。
2. 系統顯示這題的中文問題、涉及資料表、參考 SQL 與預期結果。
3. 使用者執行查詢，取得符合條件的病例清單。
4. 把查詢條件從「主證」改成「所有證型」，重新執行。
5. 系統標出新增的病例，解釋次證造成結果差異的原因。

此場景連接到後續 ERD、題目與結果比較，形成完整故事。

### 2.4 病例資料內容

以中國醫門診教學病例的症狀、證型、舌象與脈象欄位為參考，編寫 48 筆教學病例。每筆病例包含年齡區間、主訴、病程、舌脈與症狀標記，並以 CASE 編號連接證型和示例方劑。

## 三、作業要求 ② 資料庫設計

### 3.1 觀念與正規化

以「一次病例」為主要資料實體；病例與症狀、證型、方劑均可能是多對多，透過中介表建模。方劑和藥材也是多對多；各名稱只在對應字典表維護，避免同一個名稱散落於大量病例列。

「沒有提到症狀」與「明確否認症狀」分開處理：`case_symptom.status = 'present'` 為觀察到，`absent` 為明確否認；不存在該關聯代表未記載。這能避免把「無頭痛」誤當成「頭痛」。

### 3.2 完整 ERD（九張表）

```text
clinical_case 1 —— N case_syndrome N —— 1 syndrome
clinical_case 1 —— N case_symptom  N —— 1 symptom
clinical_case 1 —— N case_formula  N —— 1 formula
formula       1 —— N formula_herb N —— 1 herb
```

四個中介表的兩端都是複合主鍵及外來鍵。每筆教學病例恰有一個主證，允許零或多個次證；示範資料設定每病例至多一個次證。病例可以沒有處方；沒有紀錄的方劑也必須留在方劑表，以示範 LEFT JOIN。

### 3.3 資料字典

**clinical_case：病例**（48 筆）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `case_id` | TEXT | PK，格式 CASE-001…CASE-048，為教學編號 |
| `age_group` | TEXT | 年齡區間：18–29、30–39、40–49、50–59、60+ |
| `tcm_disease` | TEXT | 中醫病名／主訴分類，例如不寐、胃脘痛；按教學資料歸類 |
| `chief_complaint` | TEXT | 簡短主訴，已改寫 |
| `present_illness` | TEXT | 短病程描述，無日期、地點與個人細節 |
| `tongue` | TEXT | 舌象摘要 |
| `pulse` | TEXT | 脈象摘要 |

**syndrome：證型字典**（8 筆）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `syndrome_id` | TEXT | PK，SY-01…SY-08 |
| `syndrome_name` | TEXT | UNIQUE，標準化證型名稱 |
| `description` | TEXT | 教學用簡要說明 |

**case_syndrome：病例與證型**（54 筆）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `case_id` | TEXT | PK、FK → clinical_case |
| `syndrome_id` | TEXT | PK、FK → syndrome |
| `syndrome_role` | TEXT | `primary` 主證或 `secondary` 次證；每病例恰一主證 |

**symptom：症狀字典**（24 筆）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `symptom_id` | TEXT | PK |
| `symptom_name` | TEXT | UNIQUE，例如失眠、胸悶、腹脹、口苦、頭痛 |
| `category` | TEXT | 例如睡眠、情志、飲食、二便、頭身 |

**case_symptom：病例症狀觀察**（預定 144 筆）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `case_id` | TEXT | PK、FK → clinical_case |
| `symptom_id` | TEXT | PK、FK → symptom |
| `status` | TEXT | `present` 或 `absent`，不記載則沒有列 |

**formula：方劑字典**（10 筆）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `formula_id` | TEXT | PK |
| `formula_name` | TEXT | UNIQUE，正規化方名 |
| `category` | TEXT | 方劑分類（依來源字典） |
| `reference_source` | TEXT | 出處／來源代碼 |

**herb：藥材與炮製品字典**（49 筆；十個方劑組成名稱去重後的聯集）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `herb_id` | TEXT | PK |
| `herb_name` | TEXT | UNIQUE，保留原方劑組成的藥材名稱，例如甘草與炙甘草分列 |
| `category` | TEXT | 分類；可為 NULL，未有佐證不補造 |
| `reference_source` | TEXT | 組成或藥材目錄來源 |

**formula_herb：方劑組成**（86 筆；依十方來源組成逐一建立）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `formula_id` | TEXT | PK、FK → formula |
| `herb_id` | TEXT | PK、FK → herb |
| `ingredient_order` | INTEGER | 便於依來源顯示組成順序 |

**case_formula：病例使用的示範方劑**（46 筆）

| 欄位 | 類型 | 規則／意義 |
|---|---|---|
| `case_id` | TEXT | PK、FK → clinical_case |
| `formula_id` | TEXT | PK、FK → formula |
| `formula_role` | TEXT | 本次使用的示例方；資料庫允許未來有多方 |

### 3.4 關聯圖應在網頁顯示的說明

- `clinical_case → case_syndrome → syndrome`：一份病例可以記錄主證和次證。
- `clinical_case → case_symptom → symptom`：同一症狀可在不同病例中呈陽性或陰性。
- `clinical_case → case_formula → formula`：查某病例用方、統計一個方劑出現多少次。
- `formula → formula_herb → herb`：查每方組成，以及哪些方劑同時包含指定藥材。

所有外來鍵應存在被參照主表中；對每個方劑的組成去重；`syndrome_role` 和 `status` 設定受限值；方劑、症狀、證型名稱保持唯一。

### 4.3 單題頁面固定內容

**左欄**：題庫分類、Q 編號、題目、難度、必要資料表、SQL 關鍵字。  
**中欄**：使用者需求 → 資料表關聯說明 → 可編輯 SQL → 執行與重設。  
**右欄／下方**：預期結果、實際結果、總筆數、運行狀態、差異高亮、錯誤訊息。  
**題目底部**：逐步解釋原查詢、修改版按鈕、比較版結果、為何改變、要記住的 SQL 規則。

### 4.4 執行規則

1. 網站載入固定教學資料作為資料庫種子；每次執行 SQL 都從同一份初始資料開始，讓差異比較不受上次操作影響。
2. 執行的是真實 SQLite，不模擬 SQL 查詢結果。
3. SQL 拼字錯誤、表格不存在、聚合函數誤用等，直接回傳 SQLite 錯誤並顯示中文提示。
4. 預期結果由固定基準查詢取得並預存或再次執行核對；每個題目都可以與實際查詢對照。
5. 預期與實際欄名不同時提示欄位差異；資料行新增／消失時標記；僅排序改變時顯示「內容相同、順序不同」。
6. 行數與每題驗證結果使用固定種子資料做自動驗收，避免文案與實際資料不一致。

## 五、作業要求 ④ 結果比較

每題至少有一個「修改後 SQL」案例，可直接點選載入。比較面板固定呈現：同一個問題、原版條件、修改條件、原版結果、修改結果、新增與減少的資料、原因。以下是**正式設計應驗證的差異**：

| 題 | 原本查詢 | 修改方式 | 變化預期 | 為什麼會變 |
|---|---|---|---|---|
| Q01 | 年齡區間 50–59、60+ | 改為包含 40–49 | 14 → 26 筆 | 放寬條件，新增 40–49 的 12 筆 |
| Q02 | 只查肝鬱脾虛「主證」 | 主證、次證都納入 | 12 → 13 筆 | 額外有 1 筆以其為次證 |
| Q03 | 失眠且 status=present | 拿掉 status 條件 | 9 → 13 筆 | 額外混入 4 筆明確否認失眠的病例 |
| Q04 | 主證與次證都 JOIN | 只保留主證 | 54 → 48 關聯列 | 六個次證關聯被排除 |
| Q05 | 每個主證分組計數 | 刪除 GROUP BY | 8 列 → 1 列，總計 48 筆主證紀錄 | 原本各證型的個別計數被合併；展示聚合範圍改變 |
| Q06 | HAVING 計數 ≥7 | 改成 ≥5 | 3 → 5 種證型 | 6 筆與 5 筆的兩組也符合門檻 |
| Q07 | 逍遙散的組成 | 查歸脾湯 | 8 → 12 個組成名稱 | JOIN 相同，篩選的方劑不同 |
| Q08 | LEFT JOIN 找未被使用的方劑 | 改成 INNER JOIN 再找 NULL | 2 → 0 筆 | INNER JOIN 事先排除右表無紀錄的方劑 |
| Q09 | 同時有當歸、炙甘草兩種 | 改為至少有一種 | 3 → 6 方 | 「兩者皆有」與「其中之一」條件不同 |
| Q10 | COUNT(case_formula.case_id) | 改成 COUNT(*) | 兩個未用方劑計數 0 → 1 | LEFT JOIN 保留一列空配對，COUNT(*) 也算這列 |
| Q11 | 查詢病例使用方劑含當歸 | 把指定藥材改為炙甘草 | 24 → 34 個病例 | 有些方含炙甘草但未含當歸；條件值改變，符合的方劑及病例隨之改變 |
| Q12 | LEFT JOIN 找尚未使用方劑的病例 | 改成 INNER JOIN 再找 NULL | 2 → 0 筆 | INNER JOIN 排除所有無處方的病例 |

Q05 的「不分組聚合」應重新指定顯示欄位，避免 SQLite 容許非分組欄位而造成看似任意的組別標籤。Q11 的兩個數字已依十個方劑的實際組成與固定示範處方分布核對：含當歸的使用紀錄為 24、含炙甘草的使用紀錄為 34。

## 八、重要設計決策與理由

1. **以中醫病例為主題**：臨床病例與症狀、證型、方劑、藥材天然有多對多關係，容易說明 JOIN、聚合和去重的目的。
2. **使用固定教學種子**：每次執行重新載入相同資料，所有題目都有可核對的答案。
3. **保留「主證／次證」**：可展示一對多查詢後列數增加，對應一份病例可有多個證型的資料結構。
4. **保留「症狀 present／absent」**：可用 SQL 表達「有症狀」與「明確沒有症狀」，讓語意與查詢差異有真實教育價值。
5. **保留未使用方劑與無方病例**：LEFT JOIN 和 NULL 的教學例子具體且可重現。
6. **藥材名字保持原來源細節**：例如「炙甘草」與「甘草」各自保留；組成數與同時包含兩藥的查詢才有明確定義。
7. **用資料關係解釋結果**：依病例方藥配對、使用次數與年齡區間，逐題說明篩選、連結與聚合的效果。
